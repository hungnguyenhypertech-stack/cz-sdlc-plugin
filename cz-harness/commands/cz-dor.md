Phase 7 of the cz-harness playbook. Argument `$1` is an RD ID, e.g. `RD-PB01-014.02`. Output artifact: `deliverables/DOR-<rd-id>.md` (e.g. `DOR-PB01-014.02.md`) — note this phase runs **once per RD**, not once per project; there is no single project-wide DOR file.

**Gate check**: refuse unless `gate-records/PB6-risk.json` is `status:"passed"` AND the RD `$1` exists under `rd/` with a `parent_req` and `parent_wbs` pointing at gated `SPEC-*` and `WBS-*` entries. The phase-gate half of this check is mechanically enforced: `hooks/guard-pipeline-order.sh` (PreToolUse) blocks any write to a per-RD `deliverables/DOR-*.md` unless `gate-records/PB6-risk.json` already shows `status:"passed"` on disk — it deliberately checks that once-per-project phase gate only, never a per-RD record, since step 7 is evaluated per RD (plan §4.3) but its immediate predecessor (step 6) is not.

7-beat loop:

1. **Context** — load RD `$1` in full: statement, AC list, module, estimate block, `content_hash`.
2. **Plan** — check the RD against all six validity rules before delegating: exactly one observable behavior; 1-3 AC; independently testable; `estimate.expected_h <= 4` and `estimate.pessimistic_h <= 6`; maps to exactly one module; no conjunction ("and"/"also"/"then also") hiding a second behavior in the statement.
3. **Delegate** — send the RD to the `test-designer` agent via Task. Instruct it to evaluate DoR strictly against the six rules plus testability of each AC (can a test case be written today, with no missing fixtures/data/environment).
4. **Execute** — `test-designer` writes `deliverables/DOR-<rd-id>.md`: pass/fail per rule, and if fail, a recommended split (see `/cz:rd` split triggers) or a rewrite of the offending AC/statement, returned as a proposal — not applied automatically. **Length scales with this RD's effective profile** (`hooks/lib/common.sh`'s `cz_effective_profile` — the RD's own `profile:` field if set, else module/project profile; see `skills/rd-decomposition/SKILL.md`'s complexity heuristic): under `light`, a passing rule gets a one-line verdict only, no narrative justification — write the paragraph-length reasoning only for a rule that actually fails, or when a PASS verdict is genuinely non-obvious and needs defending. Under `standard`/`heavy`, the fuller narrative-per-rule form (as in `templates/DOR-PB0X.md`'s worked example) is expected. This mirrors gate-engine's own profile matrix ("AI review: light=1 pass short checklist | standard=1 pass full checklist") applied to DoR instead of gate 1.
5. **Gate** — read `human_gates.dor` from `config/gates.yaml` (default `false`). If `true`: DoR needs human confirmation before the RD enters `/cz:build`, on top of the AI review already run in Execute; approval writes `gate-records/<rd-id>-dor.json` with `{rd_id, status, approver, timestamp}`. If `false`: the AI review from Execute is authoritative — auto-write the same record with `{approver:"auto"}` directly from `test-designer`'s pass/fail verdict. Either way, once the gate record's `status` is `"passed"`, check `$1`'s `depends_on` list (if present): if every listed RD is `state: accepted`, edit `rd/$1.md`'s frontmatter to set `state: ready`; if any listed RD is not yet `accepted`, set `state: blocked_dep` instead (re-check on each dependency's later transition to `accepted` — a `blocked_dep` RD needs no fresh DoR run, just this same dependency check re-applied, moving it `blocked_dep -> ready`). Both `draft->ready`/`draft->blocked_dep` and `blocked_dep->ready` are valid per `hooks/guard-state-transition.sh`'s transition table; that hook is the sole enforcer, so an illegal current state fails this edit rather than being silently accepted. This is the only place in the pipeline that performs the `ready` write — without it the RD stays `draft` forever and can never be claimed, regardless of how many DoR reviews pass. A failing DoR leaves `state` untouched at `draft`/`blocked_dep`.
6. **Log** — append a Delivery Log entry to `deliverables/understanding-log/rd/$1.md` (create it from `templates/UNDERSTANDING-LOG.md` if this is the RD's first entry; fragment-local `UL-<nnn>` numbering, not the old project-wide counter) for this RD's DoR result. A full Understanding Gate question is not required per-RD at this granularity, but any DoR **failure** must append a note explaining why, tagged to `$1`. Writing to this RD's own fragment file, rather than a single project-wide log, is what lets multiple RDs' DoR reviews run concurrently (under `bounded`/`wave` concurrency) without racing on the same file.
7. **Iterate** — a failing DoR sends the RD back to `/cz:rd` for splitting/rewriting; it may not proceed to `/cz:build` in its current form.

Exit condition: `gate-records/<rd-id>-dor.json` has `status:"passed"` AND `rd/<rd-id>.md`'s `state` is `ready`. Only then may `/cz:build $1` run (its claim step's `ready -> claimed` transition otherwise has no valid `ready` state to move out of). Because this runs per-RD, a project can have dozens of `DOR-*.json` gate records active simultaneously across different RDs.
