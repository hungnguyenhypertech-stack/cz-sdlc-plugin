---
description: Orchestrator — drive phases and RDs unattended until a human gate, hard-stop, budget cap, or exhaustion stops it
argument-hint: [project-code]
allowed-tools: Read, Write, Edit, Bash, Grep, Glob, Task
---

The unattended driver for the cz-harness playbook. Project code is `$1` (e.g. `PB01`). This command **produces no artifact of its own** — it only sequences the existing phase commands and agents in exactly the order a human currently invokes them by hand, and it stops by itself the moment the harness says a human is needed. It adds no authority: every gate, hook, and `one_way_ratchet` invariant in `config/gates.yaml` applies to work driven from here identically to work driven manually.

**Gate check**: refuse unless `config/gates.yaml` and `state/board.json` both exist for `$1` (i.e. `/cz:init` has run). Refuse to start if `state/board.json` already lists an open hard-stop — resolve it first (see `docs/OPERATOR-GUIDE.md` §6); `/cz:run` never closes one.

Run this loop until a stop condition in step 6 fires:

1. **Context** — read `config/gates.yaml` in full (`human_gates`, `concurrency`, `budgets`, `one_way_ratchet`), `state/board.json` (wave, gate profile, `cost.usd_total`, `hard_stops[]`, per-RD state), `state/locks/*.lock` for current in-flight count, and `gate-records/*.json` to establish which project-level phases have already passed. Re-read `config/gates.yaml` fresh on **every** iteration — a mid-run edit takes effect on the next unit of work, per the last `one_way_ratchet` line; never cache the `human_gates` block across iterations.
2. **Stop-check (before claiming anything)** — evaluate every condition in step 6 against the context just loaded. If any fires, go straight to step 7. This ordering is what guarantees `/cz:run` can never claim work it was already supposed to have stopped before.
3. **Schedule** — dispatch the `sub-pm` agent via Task, asking it for exactly one next eligible unit of work: either (a) the next unstarted project-level phase in playbook order — 0 `/cz:scope`, 1 `/cz:spec`, 2 `/cz:modulemap`, 3 `/cz:arch`, 4 `/cz:wbs`, 5 `/cz:estimate`, 6 `/cz:risk`, then `/cz:rd` for the current wave, and 10 `/cz:report` once the wave's RDs are accepted — or (b) the next claimable RD, respecting `concurrency.max_in_flight` and the hazard serial-drain rule (a `hazard: true` RD may be handed back only when in-flight is zero — `hooks/guard-claim-lock.sh` is the backstop, not the scheduler; do not attempt a claim it would deny). `sub-pm` returns a scheduling decision only — it does not approve, does not commit a split, does not write a gate record, does not write the claim lock or flip an RD's state to `claimed`, and does not dispatch `test-designer`/`dev`/any other pipeline agent via Task itself (see `agents/sub-pm.md` hard rules 2, 4, 6 and 7). This command (steps 4-5 below), not `sub-pm`, is what actually claims and drives the returned unit of work.
4. **Execute (project-level phase)** — if step 3 returned a phase, first read that phase's `human_gates` key (`scope`, `spec`, `modulemap`, `arch`, `wbs`, `estimate`, `risk`, `rd_commit`, `report`) — if it is `true`, stop per step 6a **without** invoking the command, so the human reviews a phase that was never half-driven. Otherwise invoke that phase's command with `$1` (`/cz:scope $1`, `/cz:spec $1`, …) and let the command run its own 7-beat loop, including its own Gate step; that command, not this one, writes `gate-records/PB<n>-<phase>.json`. Treat a refusal from the command (missing input artifact) as a scheduling error and surface it, do not retry blindly.
5. **Execute (RD)** — if step 3 returned an RD, drive its full sequence in order: `/cz:dor <rd-id>`, then — only on `gate-records/<rd-id>-dor.json` `status:"passed"` — `/cz:build <rd-id>`, then `/cz:gate <rd-id>` per `/cz:build`'s own step-10 handoff. A `fail` verdict at gate returns the RD to `/cz:build <rd-id>` exactly as `commands/cz-gate.md` step 10 specifies (state `red`, lock restamped `cz-build`); a failing DoR returns it to `/cz:rd` and the RD is **not** re-driven this iteration. Never set `CZ_ACTING_AGENT`/`CZ_ACTIVE_RD` yourself to shortcut a claim, never write a lock file directly, and never pre-write a `gate-records/*.json` a command is about to write.
6. **Stop conditions (any one halts the loop — automatically, with no human turn needed to trigger the halt)**:
   - **a. Human gate.** The next unit's relevant `human_gates.<key>` is `true` in `config/gates.yaml`. `human_gates.scope` defaults to `true` when the key is **absent** from the file — gates.yaml documents Phase 0 as the project's last unconditional human checkpoint, and this command must treat an absent key as `true` and stop, never as permission to proceed. Same for a per-RD `human_gates.dor`/`human_gates.gate` of `true`: stop before the blocking beat, do not answer the Understanding Gate question on the human's behalf.
   - **b. Hard-stop.** A new `HS-<proj>-<nnn>` appears in `state/board.json`'s `hard_stops[]` or a `hardstop` event is appended to `telemetry/events.jsonl` by any agent (ba/sa/dev may raise one — see their hard rules). Stop immediately; do not start another unit.
   - **c. Budget cap.** `state/board.json`'s `cost.usd_total` has reached `budgets.per_wave_usd_hard`. Claim **no new** RD or phase; let already-in-flight work finish its current `/cz:build`→`/cz:gate` sequence, then stop. (`budgets.per_rd_usd_soft` is amber only — it flags, it does not stop the loop.)
   - **d. Exhaustion.** `sub-pm` reports no eligible phase and no claimable RD — either everything in the wave is accepted (run `/cz:report $1` if Phase 10 has not passed), or every remaining RD is blocked on a dependency, a stale claim, or a hazard drain that cannot complete.
7. **Report** — on stopping, print: which stop condition fired, the exact unit it stopped **at** (phase name or RD id), the units completed this run, current `cost.usd_total` against `budgets.per_wave_usd_hard`, and the single next manual action — e.g. "blocked at Phase 0: `human_gates.scope` is `true` — a human must review `deliverables/SCOPE-$1.md` and approve before `/cz:run` can continue", or "blocked at `RD-PB01-014.02`: `human_gates.gate` is `true` — review `deliverables/reviews/` and answer the Understanding Gate question in `deliverables/understanding-log/rd/RD-PB01-014.02.md`". Point the human at `deliverables/index.html` and `/cz:status` for the full picture.

**This command never**: flips or writes any `human_gates` value (or any other line of `config/gates.yaml` — that is a human commit, `agents/sub-pm.md` hard rule 3); approves a gate or writes `human_approved: true`; commits an RD split; bypasses or reorders any hook (`guard-claim-lock.sh`, `guard-red-before-green.sh`, `guard-rd-freeze.sh`, `guard-role-boundaries.sh`, `guard-state-transition.sh`, `detect-hazard.sh`, `guard-secrets.sh`); or changes the semantics of any phase command it invokes. If a hook denies an action, that denial is the answer — surface it via step 7 and stop.

Exit condition: the loop has halted on exactly one of 6a-6d, that reason and the required next manual action have been reported, and no gate record, lock, or `config/gates.yaml` line was written by this command itself. Re-running `/cz:run $1` after the human resolves the reported blocker resumes from the next eligible unit — it is safe to re-run and never re-drives an already-passed gate.
