---
description: Scaffold a new cz-harness project runtime and choose gate profile and concurrency mode
argument-hint: [project-code]
allowed-tools: Read, Write, Bash, Grep, Glob
---

Scaffolds the runtime folders for a new project, `$1` (e.g. `PB01`). This is not one of the 11 phase steps — it is the prerequisite for `/cz:scope` to have somewhere to write.

1. **Context** — check whether a project runtime already exists (look for `state/board.json`). If it does, refuse and point to `/cz:status` instead of re-scaffolding over live state.
2. **Plan** — decide the two project-wide settings that shape every later command's behavior:
   - **Gate profile**: `light` (warn-only on orphans, minimal review overhead — for spikes/prototypes), `standard` (block on current-wave orphans, AI review always + security review only when hazard/leash triggers it — default), or `heavy` (block on current-wave orphans, security review mandatory regardless of hazard/leash, mandatory refactor pass every RD). Profile does not control human sign-off — that is `human_gates` in `config/gates.yaml` (see below), a separate per-phase toggle.
   - **Concurrency mode**: `serial` (one RD claimed at a time), `bounded` (up to N RDs in flight, N set here, no two touching the same module simultaneously), or `wave` (all near-term-wave RDs may be claimed in parallel, gated only by module dependency order from `deliverables/MODULEMAP-$1.md`).
3. **Execute** — create the directory tree: `rd/`, `tests/`, `evidence/`, `gate-records/`, `telemetry/`, `state/`, `config/`, and `deliverables/` (with `deliverables/adr/`, `deliverables/reviews/security/`, `deliverables/coverage/`, `deliverables/_assets/`, `deliverables/understanding-log/`, `deliverables/understanding-log/rd/`). `deliverables/` is where every agent's narrative/report output lives — see `docs/DELIVERABLES.md`; `reviews/**` is nested under it (`deliverables/reviews/**`), not a separate top-level folder. Write `config/gates.yaml` seeded with the chosen `profile`, `delegation_ceiling`, `concurrency`, `hazard_paths`, `budgets`, and a `human_gates` block defaulting every phase key to `true` (the plugin's own conservative default — a project may lower individual phases afterward by editing this file directly; that edit needs no gate of its own). Write `state/board.json` seeded with `{project: "$1", wave: 0, gate_profile, concurrency_mode, rds: {}}` and an empty `telemetry/events.jsonl`. Copy the plugin's `templates/deliverables/style.css` to `deliverables/_assets/style.css` (the render hook keeps this in sync on every later write, so this copy just makes it present immediately). `deliverables/understanding-log/` replaces the old single `UNDERSTANDING-LOG.md` file: it holds one fragment per phase gate (`init.md`, `scope.md`, `spec.md`, `rd-commits.md`, `report.md`, `audit.md`, `rebuild-state.md`, `viva.md`) plus `rd/<rd-id>.md` per RD (written by `/cz:dor` and `/cz:gate`) — this keeps concurrent RDs (under `bounded`/`wave` concurrency) from racing on a shared file, since each RD and each phase owns its own fragment with fragment-local `UL-<nnn>` numbering. Create `deliverables/understanding-log/init.md` from `templates/UNDERSTANDING-LOG.md`, header only, no entries yet.

   Two further copies are **required**, not cosmetic — both were previously missing and each silently disabled a whole subsystem:
   - Copy the plugin's `config/hazard-paths.yaml` to `config/hazard-paths.yaml`. `hooks/detect-hazard.sh` reads this file and **disables hazard detection entirely when it is absent** — writes to auth/migration/secret/payment paths then escalate nothing, emit no `hazard_escalation` telemetry, and trigger no security gate, with no signal that anything is off. Keep its globs in agreement with `config/gates.yaml`'s `hazard_paths` (`/cz:audit` checks that they match).
   - Copy the plugin's `board/` directory (`board.html`, `build-audit-index.py`) to `board/` in the project. `board/board.html` fetches `../state/board.json`, `../gate-records/index.json` and `../deliverables/index.json` — all **relative to its own location** — so `/cz:board` can only serve it from inside the project tree. Without this copy `/cz:board`'s documented URL 404s.

   Finally, seed `gate-records/index.json` by running `python3 board/build-audit-index.py` from the project root, so the board's Audit &amp; Outcomes tab has a (initially empty) file to fetch instead of erroring on a 404.
4. **Gate** — human confirms the chosen profile, concurrency mode, and initial `human_gates` defaults before the scaffold is finalized (a wrong profile choice is expensive to change mid-project). No AI/security review at init.
5. **Log** — append the first Delivery Log entry to `deliverables/understanding-log/init.md` recording the chosen profile/mode and why.
6. **Iterate** — if the human wants to change profile/mode later, re-run `/cz:init $1` only if no RDs exist yet; otherwise the change must be recorded as a decision in `deliverables/understanding-log/init.md` rather than silently rewriting `state/board.json`.

Exit condition: `state/board.json`, `config/gates.yaml`, `config/hazard-paths.yaml`, `board/board.html`, `gate-records/index.json`, `deliverables/understanding-log/init.md`, and the runtime folders (`rd/`, `tests/`, `evidence/`, `gate-records/`, `telemetry/`, `state/`, `deliverables/`, `deliverables/understanding-log/`, `deliverables/understanding-log/rd/`) exist. Verify `config/hazard-paths.yaml` and `board/board.html` specifically — a scaffold missing either looks healthy but has hazard detection or the live board silently disabled. `/cz:scope $1` may now run.
