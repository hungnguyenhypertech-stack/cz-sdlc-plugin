Phase 8 of the cz-harness playbook. Argument `$1` is an RD ID, e.g. `RD-PB01-014.02`. Outputs: a working slice of code plus `deliverables/DEVBOOK-<rd-id>.md`.

**Gate check**: refuse unless `gate-records/<rd-id>-dor.json` is `status:"passed"`. Refuse if any linked test case for `$1` is flagged stale by the `guard-rd-freeze` hook (writes are blocked anyway, but this command should not even attempt to start the loop). The DoR-gate half of this check is mechanically enforced: `hooks/guard-pipeline-order.sh` (PreToolUse) blocks any write to `deliverables/DEVBOOK-<rd-id>.md` unless THIS SAME RD's own `gate-records/<rd-id>-dor.json` already shows `status:"passed"` on disk — a per-RD check, not the once-per-project phase gates (plan §4.3).

This command runs the exact inner loop below. It is a strict sequence — no step may be skipped or reordered, and the two enforcement hooks are load-bearing, not advisory.

1. **Claim** — run `CZ_ACTING_AGENT=cz-build CZ_ACTIVE_RD=$1 "${CLAUDE_PLUGIN_ROOT}/hooks/guard-claim-lock.sh" "$1"` to take the lock (this is the one hook not wired into `hooks.json` — see its header comment — so it must be invoked directly, here, at claim time). This is also what makes the live board and telemetry show a real agent name instead of `unknown`: every hook that fires afterward (for the rest of this loop's tool calls) resolves identity by reading `state/locks/$1.lock` when no env var is set for that call (env vars set here do not persist to later, separate tool calls or into the Task-dispatched sub-agents below) — see `hooks/lib/common.sh`'s `cz_sole_lock_agent`/`cz_sole_lock_rd`. The hook itself appends the `rd_claim` telemetry event on a genuinely new claim (nothing further to do here for that); also mark RD `$1` as `in_progress` in `state/board.json` so `/cz:status` shows it live.
2. **Context** — load RD `$1`'s statement, AC list, and `content_hash`. The `dev` agent must **not** be given `tests/**` contents at any point in this loop — it has zero context of the test cases.
3. **Delegate (test-designer)** — before dispatching, run `"${CLAUDE_PLUGIN_ROOT}/hooks/restamp-lock.sh" "$1" test-designer` so the lock (and therefore the board/telemetry) reflects who's actually acting, not the generic `cz-build` loop name. Then dispatch the `test-designer` agent via Task with only the RD's AC list. It writes test cases under `tests/**` for `$1`, one TC per AC (1-3 TCs), each TC tagged with the RD's `content_hash`.
4. **Red proof** — run the new tests with Bash. They **must fail** (no implementation exists yet). Capture the raw run output to `evidence/RD-<rd-id>/tests-red-vN.log`, hash-tagged in the log header to `$1`'s `content_hash`. If the tests pass at this stage, stop — the TC is invalid (testing nothing) and must be sent back to `test-designer`. Once a genuine red is confirmed, append a `test_red` telemetry event (`cz_emit_event`, `{rd:"$1", event:"test_red", result:"ok"}`) — this is the only reliable signal (besides the `agent_dispatch` noise) that this RD's build loop actually reached this stage; without it, `/cz:rebuild-state`/`/cz:audit` cannot distinguish "RD really went through red-green" from "board/gate-records say accepted but telemetry shows nothing."
5. **Guard** — `guard-red-before-green` blocks any `src/**` write for this RD unless a matching red log exists for the current `content_hash`. Do not attempt to bypass it.
6. **Delegate (dev)** — before dispatching, run `"${CLAUDE_PLUGIN_ROOT}/hooks/restamp-lock.sh" "$1" dev` to hand the lock's identity off from `test-designer` to `dev` (same reason as step 3). Then dispatch the `dev` agent via Task with the RD statement and AC only (never the test file contents). `tests/**` is read-only to `dev`. Instruct `dev` to implement the minimum code to satisfy the AC, and to annotate every touched `src/**` file/function with the RD ID `$1` (e.g. `// RD-PB01-014.02`) — this annotation is what `/cz:report`'s orphan check for "src/** files with no RD annotation" verifies later.
7. **Green proof** — run the same tests again with Bash. They **must pass**, and the test file bytes must be **byte-identical** to the red run (diff the test source, not just re-run it) — if `test-designer` or anyone else edited a TC between red and green, this loop is invalid and must restart from step 3 (including its restamp). `guard-rd-freeze` blocks writes if a linked TC goes stale mid-loop (e.g. someone edits AC after tests are written). Once green is confirmed byte-identical, append a `test_green` telemetry event (`cz_emit_event`, `{rd:"$1", event:"test_green", result:"ok"}`), same rationale as step 4's `test_red`.
8. **Refactor (optional)** — `dev` may refactor `src/**` for `$1` as long as tests stay green on every save; re-run tests after each refactor pass. Lock stays stamped `dev` throughout.
9. **Coverage re-verification (test-designer)** — run `"${CLAUDE_PLUGIN_ROOT}/hooks/restamp-lock.sh" "$1" test-designer` to hand the lock from `dev` to `test-designer`, then dispatch `test-designer` via Task with the post-implementation state: the RD's AC list, the test cases under `tests/**` for `$1`, and the green run from step 7. `test-designer` re-verifies that every AC item has a corresponding TC and that no TC has drifted since the red run, then writes its findings to `deliverables/coverage/<rd-id>.md`. This file is mechanically required by `hooks/guard-state-transition.sh` before the `green->ai_review` transition is permitted — the gate cannot begin until it exists on disk. This step cannot be skipped or deferred to `/cz:gate`.
10. **DEVBOOK** — run `"${CLAUDE_PLUGIN_ROOT}/hooks/restamp-lock.sh" "$1" cz-build` to hand the lock back to the outer loop, then write/append `deliverables/DEVBOOK-<rd-id>.md`: red log path, green log path, files touched, refactor notes, and the final `content_hash` used throughout.
11. **Handoff** — this command does not self-gate. It ends by handing off to `/cz:gate $1`.

Exit condition: a green test run byte-identical in test source to the red run, `deliverables/coverage/<rd-id>.md` written by `test-designer`, `deliverables/DEVBOOK-<rd-id>.md` written, and control handed to `/cz:gate`. No `deliverables/understanding-log/rd/<rd-id>.md` entry is required from this command alone — `/cz:gate` appends the Understanding Gate question for this RD.
