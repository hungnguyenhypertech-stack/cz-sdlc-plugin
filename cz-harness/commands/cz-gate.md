Phase 9 of the cz-harness playbook. Argument `$1` is an RD ID, e.g. `RD-PB01-014.02`. Output: `gate-records/<rd-id>-gate.json` plus an appended question in `deliverables/understanding-log/rd/$1.md`.

**Gate check**: refuse unless `deliverables/DEVBOOK-<rd-id>.md` exists and its green run is byte-identical to its red run per `/cz:build`'s record. This command enforces a **fixed order** — steps below may not be reordered or skipped, only added to (security review is conditional, never removed once triggered).

1. **Context** — load `deliverables/deliverables/DEVBOOK-<rd-id>.md`, the red/green logs under `evidence/RD-<rd-id>/`, the diff of `src/**` files touched, and the RD's module entry within `deliverables/RISK-<proj>.md` (hazard + leash rating for the RD's module).
2. **Plan** — determine whether a security review is required: triggered if the module's hazard rating is `high` or its leash rating is `A+` (tightened leash — hazard / heavy-profile oversight) per `deliverables/RISK-<proj>.md`/`deliverables/DELEGATION-MAP-<proj>.md`. Record this decision explicitly in the gate record before proceeding.
3. **Claim + state transition (before AI review)** — this makes the live board/telemetry show a real acting agent during gate, and moves the RD out of `state: green`'s "done, awaiting review" ambiguity into the `in_review` bucket, mirroring `/cz:build`'s own step 1: if `state/locks/$1.lock` does not already exist (gate invoked standalone, not chained from `/cz:build`'s handoff), claim it via `guard-claim-lock.sh "$1"`; otherwise it already exists (typically still stamped `cz-build` from the build handoff) — restamp it to `ai-reviewer` via `restamp-lock.sh "$1" ai-reviewer`. Then set RD `$1`'s frontmatter `state: ai_review` (schema-valid state, bucketed as `in_review` by `hooks/project-state.sh`). Every hook firing during the dispatch in the next step resolves identity from this lock, so the board shows `ai-reviewer` as the live agent for the duration of the review — not `unknown` and not stale.
4. **Delegate — AI review (always runs first)** — dispatch the `ai-reviewer` agent via Task with the diff, DEVBOOK, and AC list. It checks: AC coverage, RD-ID annotation on touched `src/**` files, no scope creep beyond the RD statement, no edits to `tests/**`. Verdict: pass/fail with findings. Record the wall-clock timestamp (`cz_now`) at which this dispatch returns — step 7 writes it as `ai_review.timestamp`, the only way the "AI review before security review before gate decision" ordering invariant becomes mechanically checkable instead of merely asserted.
5. **Claim + state transition (before security review, conditional)** — only if step 2 flagged hazard=high or leash=A+: restamp the lock to `sec-reviewer` via `restamp-lock.sh "$1" sec-reviewer`, and set RD `$1`'s frontmatter `state: sec_review` (still bucketed `in_review`). Then dispatch `sec-reviewer` via Task with the same diff. It checks for injection, secrets, auth bypass, unsafe external calls. If not triggered, record `security_review: "not_required"` in the gate record (with `timestamp: null` — a review that never ran has no completion time), skip this step's lock/state changes entirely, and move on — do not fabricate a pass and do not stamp a state/lock change for a review that didn't run. If it does run, record the wall-clock timestamp at which this dispatch returns for step 7's `security_review.timestamp`, same rationale as step 4's `ai_review.timestamp`.
6. **Gate decision (always runs last)** — read `human_gates.gate` from `config/gates.yaml` (default `false`). If `true`: present the AI (and security, if run) verdicts to the human for final approval/rejection — this cannot be skipped while the setting is `true`, even if AI and security both pass. Optionally reflect this wait as `state: human_review` (bucketed `in_review`) until the human responds. If `false`: this phase closes automatically once AI review (and security review, if triggered) both read `pass`/`not_required`. Either way, any `fail` at the AI or security stage blocks approval (see step 9).
7. **Execute** — write `gate-records/<rd-id>-gate.json`: `{rd_id, ai_review: {verdict, findings, timestamp}, security_review: {verdict|"not_required", findings, timestamp|null}, gate_decision: {approver:"auto"|<human>, decision, timestamp}, order_enforced: true}`. The three timestamps (`ai_review.timestamp` from step 4, `security_review.timestamp` from step 5 or `null` if `not_required`, `gate_decision.timestamp` from this step) must be chronologically non-decreasing — that ordering is what `order_enforced: true` is actually claiming; it is no longer just an assertion. If `rd/$1.md`'s frontmatter has `pending_verification: true`, copy it (and `pending_verification_reason`) into this gate record verbatim — `hooks/guard-state-transition.sh` already refuses `human_review->accepted` while it's still true (step 8 below), but the record should carry the fact forward regardless of decision so `/cz:report`'s RTM can surface it (see `commands/cz-report.md` step 2).
8. **Resolve state + lock (after decision)** — this is what actually closes out the `in_review` bucket, and must not be skipped even though it's not a narrative deliverable: if `gate_decision.decision` is `approved`, run `hooks/compute-estimate-variance.sh "$1"` and embed its JSON output as `estimate_variance` in `gate-records/<rd-id>-gate.json` (planner's pre-build `estimate.expected_h`/`.pessimistic` from `rd/$1.md` vs. this RD's actual **active** work time — mechanically derived from `telemetry/events.jsonl`'s own timestamps for `$1`, with idle/blocked gaps over `LOCK_TTL_S` excluded so time queued behind `max_in_flight` or waiting on a human gate doesn't get misread as work-effort overrun; raw wall-clock span is also kept in the record as `actual_h`. No new capture needed, nothing estimated or guessed; this is the audit point that lets a later `/cz:audit` or WEEKLY rollup judge whether planner's estimates run systematically high or low). This must run **before** the lock is released, since the script reads telemetry which release-lock.sh's own `rd_release` event would otherwise fold into (harmless either way, but computing first keeps "the record closes over what actually happened" unambiguous). Then set RD `$1`'s frontmatter `state: accepted` and release its claim lock via `release-lock.sh "$1" accepted` (not a plain `rm` — this durably records the release in telemetry as `rd_release` before the lock file disappears; without it there is no trail at all once the file is gone) — the RD's work is done, nothing should keep holding it. If `decision` is `rejected`, emit a `gate_rejected` event (`cz_emit_event`, `{rd, event:"gate_rejected", result:"back_to_build"}`) before restamping — a plain `lock_restamped` from `ai-reviewer`/`sec-reviewer` back to `cz-build` reads identically to a normal handoff, so the rejection itself needs its own explicit marker — then set `state: red` (back into the build loop; do not use `rejected` — that state is reserved for a terminal, non-retrying kill, not a fixable gate failure) and restamp the lock back to `cz-build` via `restamp-lock.sh "$1" cz-build`, since `/cz:build` is the next thing to touch this RD per step 9 below (no `estimate_variance` is computed on a rejected decision — the RD isn't done, so there is no real "actual" yet). Either way, clear any now-stale heartbeat entries for agents that are not actually still working (e.g. `ai-reviewer`/`sec-reviewer`'s `.hb` files once their dispatch has returned) so the board does not keep showing them as `executing` after they've finished.
9. **Log** — append a Delivery Log entry to `deliverables/understanding-log/rd/$1.md`, and append a new **Understanding Gate** question specific to this RD (e.g. "Explain in plain terms what `$1` now lets a user do, and one way it could still fail."). Requires a human-authored answer before the RD is considered closed only when `human_gates.gate` is `true`; otherwise logged for visibility.
10. **Iterate** — any `fail` verdict at any stage sends the RD back to `/cz:build $1` (re-enter the red-green loop); it does not retry the gate directly. Step 8 already left `state: red` and the lock stamped `cz-build` for exactly this handoff.

Exit condition: `gate-records/<rd-id>-gate.json` has all applicable stages at `pass`/`not_required` as appropriate and `gate_decision` recorded, RD `$1`'s frontmatter `state` reflects the outcome (`accepted` or `red`, never left at `ai_review`/`sec_review`/`human_review`), and its claim lock is either released (`accepted`) or handed back to `cz-build` (`red`) — AND, only when `human_gates.gate` is `true`, the RD-specific Understanding Gate question answered by a human in `deliverables/understanding-log/rd/$1.md`.
