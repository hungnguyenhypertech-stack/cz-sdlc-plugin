---
description: Regenerate state/board.json purely from telemetry/events.jsonl
argument-hint: [project-code]
allowed-tools: Read, Write, Bash, Grep, Glob
---

Rebuilds `state/board.json` for project `$1` from `telemetry/events.jsonl` alone, exercising the invariant that the board projection is pure and rebuildable — no other input is consulted, not even the existing `state/board.json`.

**Known gap (found by `/cz:audit`, 2026-07-29; schema/vocabulary reconciled 2026-07-29, audit findings C7/M5):** the actual deterministic implementation wired into `hooks.json` (`hooks/project-state.sh`, which runs on every `PostToolUse` and is what really keeps `state/board.json` live) does **not** replay `telemetry/events.jsonl` for RD state/module/summary/assigned_agent/leash/time-in-state — it derives those directly from `rd/*.md` frontmatter, `gate-records/*.json`, and `state/heartbeats/*.hb`, and only sums `telemetry/events.jsonl` for the one figure those sources can't supply (per-RD `cost_usd`, audit finding C8). This is a deliberate hybrid design, not drift — see `schemas/board-state.schema.json`'s title/description, which used to (incorrectly) claim a pure "from the log alone" rebuild. The **real** telemetry vocabulary — the event names `telemetry-event.schema.json`'s `event` enum actually validates and that hooks/command files actually emit — is: `agent_dispatch`, `agent_heartbeat` (emit-telemetry.sh, only on a real RD/agent transition, not every tick), `rd_claim`/`rd_release` (guard-claim-lock.sh/release-lock.sh), `lock_reclaimed` (guard-claim-lock.sh, TTL-expired reclaim), `lock_restamped` (restamp-lock.sh, mid-claim role handoff), `test_red`/`test_green` (this command's own inner loop, `commands/cz-build.md` steps 4/7), `gate_rejected` (`commands/cz-gate.md` step 8), `hazard_escalation` (detect-hazard.sh), `agent_error` (guard-role-boundaries.sh). This command is a **cross-check / recovery path** over that real vocabulary, not the board's actual source of truth, and it is honestly a **partial** replay: nothing in this plugin yet emits project/wave/profile-level lifecycle events (`project_init`, `wave_advance`, `rd_committed`, `profile_set`, terminal `rd_done`/`rd_blocked`), so a full from-scratch reconstruction of `project`/`wave`/`profile`/per-RD terminal state from telemetry alone is not actually possible today — those fields must still come from `state/board.json`'s prior value or from `gate-records/PB0-scope.json`/`config/gates.yaml` directly, same as `hooks/project-state.sh` does. Treat any mismatch this command finds in the fields it CAN replay (claim/release/handoff/red-green/gate-rejection timing per RD) against a fresh `project-state.sh` run as the primary signal; a mismatch may just mean an event was never emitted for some transition, which is itself worth logging (step 5) but is not automatically "the board is wrong."

1. **Context** — read `telemetry/events.jsonl` from the first event to the last. Do **not** read the existing `state/board.json` as an input (that would defeat the purpose of a from-scratch rebuild); it may only be read afterward, for comparison.
2. **Plan** — replay events in order: `rd_claim`, `agent_heartbeat`, `test_red`, `test_green`, `lock_restamped`, `gate_rejected`, `rd_release`, `lock_reclaimed`. Each event type has a deterministic effect on the per-RD projection (e.g. `rd_claim` sets `rds[rd_id].state = "claimed"` and `assigned_agent`). `project`/`wave`/`profile` are NOT replayed from telemetry (see the known-gap note above) — carry them over from the existing `state/board.json` or from `gate-records/PB0-scope.json`/`config/gates.yaml`, and say so explicitly in step 5's log rather than silently inventing them from the event stream.
3. **Execute** — fold the event stream into a fresh in-memory per-RD projection, merge it with the carried-over project/wave/profile fields, then write the result to `state/board.json`, overwriting the current file. Preserve `content_hash`/`gate_profile`/`concurrency_mode` fields exactly as sourced in step 2 — never invent defaults if a value is missing (surface that as a gap instead).
4. **Gate** — before overwriting, diff the freshly rebuilt board against the previous `state/board.json`. If there's a mismatch, print it and ask for human confirmation before overwriting — an unexpected mismatch might mean `events.jsonl` is incomplete (e.g. truncated) rather than that the old board was wrong.
5. **Log** — append a Delivery Log entry to `deliverables/understanding-log/rebuild-state.md` noting the rebuild and whether a mismatch was found and confirmed.
6. **Iterate** — if `events.jsonl` itself looks corrupted or truncated (e.g. a claim with no matching init), stop and hand off to `/cz:audit` rather than guessing.
7. **Note** — this command is the recovery path referenced by `/cz:board` and `/cz:audit` whenever the live board and telemetry disagree; it is intentionally the *only* place that writes `state/board.json` wholesale (other commands should append events, not hand-edit the board).

Exit condition: `state/board.json` reflects a full, order-preserving replay of `telemetry/events.jsonl`, confirmed by the human if it diverged from the prior file.
